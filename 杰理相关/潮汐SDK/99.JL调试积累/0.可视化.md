
结论：

根据当前 FLASH INFO 日志分析，如果物理 Flash 为 16Mbit，即 2MB，地址空间为 `0x000000 ~ 0x200000`。

当前 Flash 布局需求为：

```text
FLASH_NEED_SIZE = 0x1FF000
```

因此整片 Flash 剩余空间为：

```text
0x200000 - 0x1FF000 = 0x1000 = 4KB
```

也就是说，当前分区布局在 16Mbit Flash 上可以放下，但整体 Flash 余量只有 4KB。

另外，日志中：

```text
FLASH_BIN_SIZE     = 0xEA000
CODE_BOUNDARY_LINE = 0xFF000
LAVE_SIZE          = 0x15000
```

可计算出代码区剩余：

```text
0xFF000 - 0xEA000 = 0x15000 ≈ 84KB
```

因此这里的 `LAVE_SIZE` 表示的是代码分区内部剩余空间，不是整片物理 Flash 的剩余空间。

最终判断：

1. 如果物理 Flash 是 16Mbit，则当前 Flash 布局整体剩余约 4KB。
2. APP 代码分区内部仍剩余约 84KB。
3. 代码区已经包含在整体 Flash 分区布局中。
4. “剩余 80K”和“剩余 4K”并不矛盾，前者是代码区剩余，后者是整片 Flash 布局后的物理剩余。
5. 当前固件可以适配 16Mbit Flash，但整体 Flash 空间已经非常接近上限，后续如需增加资源区、VM、BTIF 或调整 OTA 布局，需要重新评估分区。

## 换32Mbit flash

```c
/* -------------------------------------------------------------------------- */
/* 片内 Flash 布局                                                            */
/* -------------------------------------------------------------------------- */

/*
 * 新主控的片内 Flash 容量为 32 Mbit，即 4 MiB（0x400000 字节）。
 * sdk_config.h 由杰理配置工具生成，目前只能生成 16 Mbit（0x200000）的配置；app_config.h
 * 会在 sdk_config.h 之后包含本文件，因此在此覆盖容量可以同时作用于链接脚本和打包配置，
 * 并且不会在配置工具重新生成 sdk_config.h 时丢失。
 *
 * 工程已开启双备份，4 MiB 配置下打包工具给出的单个代码区分界线为 0x1FF000；
 * 当前 CODE0 为 0x102000，剩余 0xFD000，满足双备份固件的空间要求。
 */
#undef CONFIG_FLASH_SIZE
#define CONFIG_FLASH_SIZE                         0x400000

/*
 * 原 2 MiB 布局的 VM 起始地址为 0x1FC000，即位于 Flash 末尾前 0x4000 处。
 * Flash 扩大到 4 MiB 后保持相同的尾部布局，所以 VM 起始地址相应改为 0x3FC000。
 * 当前 TCFG_VM_SIZE 为 8 KiB，打包结果中 VM 占用 0x3FC000~0x3FE000，随后
 * 0x3FE000~0x3FF000 为 BTIF 保留区。
 */
#define CONFIG_VM_ADDR                            0x3FC000
```

# os_taskq_post_type 死机分析

## 根因

JL 内核 `Q_CALLBACK` 的消息格式是 **`{callback, arg_count, args...}`** —— `msg[1]` 是参数个数，不是参数值。JL SDK 全局所有原生代码统一用 `argc=3`、`msg[1]=1`。

`rdx_os_task_post_callback` 实现时错误地用了 `argc=2`、`{callback, arg}`，把参数值直接塞进 `msg[1]`。内核把 `arg`（一个指针值）当作参数个数解读，然后从 `msg[2]` 取参数。由于旧格式没有合法的 `msg[2]`，回调收到的 `priv` 是队列缓冲区里的残留值。

**这条路径从 day 1 就是错的。** `67c8ecc` 没炸只是因为残留值碰巧指向 CPU 可写内存，`msg->busy = 0` 静默损坏了别处。`1996287` 改了二进制布局后，残留值固定为 `app_core` 栈地址；第二次 BLE 连接时回调被 CPU1 执行 → 写不进 CPU0 栈 → `cpu1 write hmem exception`。

## 修法

两个 port 的 `rdx_os_task_post_callback` 对齐 JL 原生约定：

```c
// 错误
int msg[2];
msg[0] = (int)callback;
msg[1] = (int)arg;
os_taskq_post_type(task_name, Q_CALLBACK, 2, msg);

// 正确
int msg[3];
msg[0] = (int)callback;
msg[1] = 1;
msg[2] = (int)arg;
os_taskq_post_type(task_name, Q_CALLBACK, 3, msg);
```

## 教训

封装底层 OS 原语时，必须以原生调用方的用法为唯一权威参考，而不能根据"看起来能工作"的测试结果反推语义。寄存器残留值会让错误代码在测试中表现为正常 —— 这种幸存者偏差比直接崩溃更危险。

# MIC的数量与单双声道的关系

有关系，但**不是一一对应的关系**。这里容易把「MIC 数量」和「声道数量」混在一起。

## 先简单理解

- **单声道（Mono）**：最终只有 **1 路音频信号**
- **双声道（Stereo）**：最终有 **2 路独立音频信号**，通常是 Left / Right
- **MIC 数量**：指物理上有几个麦克风传感器

所以：

| MIC 数量 | 输出声道 | 是否可能                                        |
| -------- | -------- | ----------------------------------------------- |
| 1 个     | 单声道   | ✅ 最常见                                        |
| 2 个     | 单声道   | ✅ 可以，两个 MIC 可以做降噪/波束成形后合成 1 路 |
| 2 个     | 双声道   | ✅ 可以，分别作为 L/R                            |
| 4 个     | 单声道   | ✅ 可以，4 MIC 做阵列处理后输出 1 路             |
| 4 个     | 双声道   | ✅ 可以，经过算法处理后输出 2 路                 |
| 2 个     | 4 声道   | ❌ 通常不可能直接产生 4 路独立物理采集信号       |

## 在嵌入式/BLE/音频芯片里尤其要注意

例如一个设备有：

> **2-MIC + 单声道输出**

这并不意味着它是双声道。

两个 MIC 可能分别采集：

```
MIC1 ─┐
      ├─> 降噪/波束成形/回声消除 ─> Mono
MIC2 ─┘
```

最终还是只有 **1 个 Audio Channel**。

而如果是：

> **2-MIC + 双声道**

可能是：

```
MIC1 ─────────> Left
MIC2 ─────────> Right
```

这种情况下才是两个独立声道。

## 单MIC也可以双声道？比如复制出来？

单 MIC 也可以输出“双声道”，但这里的双声道本质上是**同一个信号复制成两路**，并不是两个独立的声音采集通道。

例如：

```
        ┌──→ Left
MIC ────┤
        └──→ Right
```

结果：

```
L = MIC
R = MIC
```

这种情况下虽然音频格式是 **2-channel / Stereo**，但实际上：

> **L 和 R 完全一样，没有真正的立体声信息。**

### 举个更实际的例子

假设 MIC 采集到：

```
MIC = [100, 200, 150, 300...]
```

复制以后：

```
Left  = [100, 200, 150, 300...]
Right = [100, 200, 150, 300...]
```

这就是**伪双声道/双通道复制**。

而真正的双声道通常是：

```
MIC1 ──→ Left
MIC2 ──→ Right
```

例如两个麦克风分别采集不同位置的声音：

```
Left  = [100, 180, 120, 250...]
Right = [80,  220, 140, 310...]
```

这样才包含左右空间信息。

# 频偏校准的几种方式

## 频偏数据的机制原理

频偏校准值保存在 BTIF 区，不在 VM。已有有效校准值时，当前 SDK 会阻止再次调整和覆盖保存，JL 蓝牙盒子的校准流程也受这个限制。因此无需擦除整个 Flash，实际擦除 BTIF 中的旧记录、断电 重启后再校准即可。 这一机制已由当前 ELF 的反汇编确认；你设备上的 BTIF 是否已被下载工具真正擦除，还没有实测证据。

- 频偏值保存在 Flash 的什么位置？ 

```c
当前工程构建出来的布局为：                                                                                                   
   区域                      Flash 地址（包含末地址）    用途

   固件、资源及双备份空间    0x000000–0x3FBFFF           程序和资源等                                                                         
  ────────────────────────  ──────────────────────────  ─────────────────────────────────                                                 
   VM                        0x3FC000–0x3FDFFF           常规持久化配置                                                                     
  ────────────────────────  ──────────────────────────  ─────────────────────────────────                                                 
   BTIF                      0x3FE000–0x3FEFFF           蓝牙频偏、蓝牙 MAC 等                                                             
  ────────────────────────  ──────────────────────────  ─────────────────────────────────                                                 
   尾部保留扇区              0x3FF000–0x3FFFFF           前面分析的 RDX 授权数据位于这里

  频偏记录内容为 2 字节 CRC + 4 字节偏移值。上述地址确认的是 BTIF 区范围，不能把 0x3FE000 直接当作频偏数值的地址，具体条目位置由 BTIF 存储层管理。
```

- 为什么硬编码设置要放在 btstack_init() 前？

```
  因为它是在给蓝牙控制器初始化提供一个默认补偿值。                                                                                             
  反汇编确认，初始化过程会读取 Flash 中的频偏记录，逻辑可以简化为：                                                                             
  bt_osc_offset_set(硬编码补偿值)                                                                                                           
      ↓                                                                                                                                   
  修改 RAM 中的默认补偿值                                                                                                                   
      ↓                                                                                                                                   
  btstack_init()                                                                                                                         
      ↓                                                                                                                                   
  控制器初始化，读取 BTIF 的频偏记录                                                                                                         
      ├─ 记录有效：用保存值覆盖默认值，并设置“已有校准值”标志                                                                                   
      └─ 记录无效或不存在：保留默认值，不设置该标志                                                                                           
  所以，放在初始化前的硬编码值，是没有有效保存值时使用的默认值；已有有效保存值时，它仍然会被覆盖。                                                   
  另外，蓝牙运行起来以后，单独调用 set() 并不会主动刷新正在使用的 PLL 补偿。盒子的调整流程还会调用相应的 PLL 补偿刷新函数。
```

- bt_osc_offset_set() 和 bt_osc_offset_save() 到底做什么？

- 为什么两个函数都改不了，蓝牙盒子也改不了？

```
当前实现有两层限制：                                                                                                                         
  第一层是校准状态限制。启动时读到有效记录，就设置标志。随后 set()、save() 都直接返回。反汇编中的经典蓝牙和 BLE 校准命令处理，也会检查同一个标志；已有校准值时，跳过调整分支。            
  这就解释了为什么原生 JL 蓝牙盒子也无法重新校准。                                                                                             
  第二层是 BTIF 写入限制。当前 btif_area_write() 只允许向尚未写入的空白条目写入，已有条目会被拒绝覆盖。因此，即使绕过上面的 RAM 标志，直接 syscfg_write()，也不能正常覆盖旧条目。                 
  这是软件实现的“擦除后才能重新写入”，不是芯片物理 OTP。
```

- 遇到这种情况，只能擦除整个 Flash 吗？ 
- 置为0就可以让盒子校准。**蓝牙mac因为使用的是自定义的所以不用怕被擦除**

```
不需要。针对这次频偏问题，清掉 BTIF 旧记录就足够。 全擦有效，是因为它同时把 BTIF 清掉了；擦除 VM 无效，是因为频偏不在那里。                           
  你可以使用：                                                                                                                                             
  #define CONFIG_BTIF_OPT 0                                                                                                               
  SDK 对此选项的定义是：0 下载时擦除指定区域，1 下载时不操作该区域。操作顺序为：                                                                   
  1. 修改源配置，重新编译。                                                                                                                 
  2. 确认生成的 isd_config.ini 中为 BTIF_OPT = 0;。                                                                                         
  3. 使用实际采用该配置、执行 BTIF 擦除的下载流程烧录。                                                                                         
  4. 断电重启，再用蓝牙盒子校准。                                                                                                             
  5. 校准完成后，将配置恢复为 1 并重新生成后续下载包，避免以后下载再次清除校准数据。                                                               
  BTIF 擦除也会影响其中的蓝牙 MAC 等数据；它与前面定位的尾部 RDX 授权数据区域不同。                                                               
  至于你添加的 -format cfg，仅写进 BAT，不能证明设备上的 BTIF 已经被擦除。目前还不能确认它失败的具体原因，也不能认定它与 BTIF_OPT 的优先级。最直接的验证是：擦除并重启后，检查 ID 110 是否
  仍能读出有效旧记录，以及校准标志是否仍为 1。这能判断问题究竟是“旧数据没有清掉”，还是另有原因.
```

## 调试纠正

```
调试时推荐多次调用 bt_osc_offset_set()，满意后再调用一次 bt_osc_offset_save() 保存。 但需要注意“增量调整”和“运行时刷新”两个条件。                   
  在 BTIF 已擦除、断电重启、尚未保存校准值 的情况下：                                                                                                   
   操作          实际效果                                                                                                                   
  ━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━                                                                                                 
   set(+10)      RAM 当前补偿值加 10                                                                                                       
  ────────────  ─────────────────────────                                                                                                 
   再 set(+5)    累计增加 15                                                                                                               
  ────────────  ─────────────────────────                                                                                                 
   再 set(-3)    累计增加 12                                                                                                               
  ────────────  ─────────────────────────                                                                                                 
   save()        将当前补偿值保存到 BTIF                                                                                                                                                      
  set() 可以多次调整，但它本身不刷新运行中的 PLL 补偿。 所以在蓝牙已经初始化后，仅反复调用 set()，不能保证测到的频偏立即改变。当前库里的盒子校准流程会在 set() 后调用对应的               
  bredr_pll_comp_reset() 或 ble_pll_comp_reset()。自行实现时，需要按对应流程刷新；这些函数的调用参数和上下文应先确认，不能直接猜测调用。             
  对于 save()，你的理解基本正确：                                                                                                           
  - 同一个 BTIF 频偏条目，在两次擦除之间只能成功写入一次。 再次调用不能覆盖旧值。                                                                 
  - save() 本身不会立即置位那个“已有校准值”标志。因此，同一次开机中，保存后 set() 可能仍能修改 RAM，但再次保存会被存储层拒绝。                       
  - 重启后，初始化读到已保存的有效记录，将标志置位，此后 set() 和 save() 都会直接返回。重新校准需要先清掉旧记录。                                                               
  推荐流程是：                                                                                                                                                    
  擦除 BTIF → 断电重启                                                                                                                     
      → set 增量调整 + 刷新 PLL → 测量
      → 重复调整，直到满意                                                                                                                   
      → save 保存一次                                                                                                                     
      → 断电重启，复测确认                                                                                                                   
  实际操作上，优先使用 JL 盒子的调整流程，最终再保存。 需要确认盒子是否每次校准结束都会自动保存；如果会，那么下一轮重新校准前仍需要擦除 BTIF。
```
