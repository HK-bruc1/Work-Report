# RDX BLE 广播字段协议

本文用于说明 RDX 设备的 BLE 广播包结构、各字段含义和手工解析方法。

参考资料：

- [BLE通讯协议_20260522.xlsx](../BLE通讯协议_20260522.xlsx)
- [rdx_ble_server.c](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_ble_server.c)
- [rdx_ble_server.h](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_ble_server.h)
- [rdx_app_config.h](../SDK/apps/common/third_party_profile/rdx_protocol/rdx_app_config.h)

## 1. 广播包由两部分组成

RDX 使用 Legacy Advertising，数据分为两部分：

```text
Advertising Data（广播数据，最大 31 字节）
+
Scan Response Data（扫描响应，最大 31 字节）
```

手机抓包工具有时会把两部分拼成一串显示。因此，看到超过 31 字节的十六进制字符串，不代表固件发送了一个超长广播包。

RDX 当前使用的总体结构为：

```text
Advertising Data
┌──────────┬────────────────────────────┐
│ Flags    │ Complete Local Name        │
│ 02 01 xx │ NN 09 [BLE Name]           │
└──────────┴────────────────────────────┘

Scan Response Data
┌───────┬────────┬──────┬─────────┬───────┬─────────┬─────────┬─────┬───────────┐
│ 1A FF │ PID[3] │ MAC  │ Id mark │ State │ Ability │ Version │ SKU │ Self mark │
│       │        │ [6]  │ [6]     │ [1]   │ [4]     │ [1]     │ [2] │ [2]       │
└───────┴────────┴──────┴─────────┴───────┴─────────┴─────────┴─────┴───────────┘
```

## 2. BLE AD Structure 的长度规则

每个 BLE 数据段都使用以下格式：

```text
Length | AD Type | AD Data
```

`Length` 只统计后面的 `AD Type + AD Data`，不包含 `Length` 自身。

例如：

```text
02 01 0A
│  │  └─ Flags 数据：0x0A
│  └──── AD Type：0x01（Flags）
└─────── 后面共有 2 字节：01 0A
```

```text
0B 09 4E 6F 74 74 61 20 4D 65 6D 6F
│  │  └────────────────────────────── "Notta Memo"，10 字节
│  └───────────────────────────────── AD Type：0x09（Complete Local Name）
└──────────────────────────────────── 后面共有 11 字节：09 + 10 字节名称
```

RDX 广播中使用的 AD Type：

| AD Type | 含义 |
| --- | --- |
| `0x01` | Flags |
| `0x09` | Complete Local Name，完整 BLE 名称 |
| `0xFF` | Manufacturer Specific Data，厂商自定义数据 |

## 3. Advertising Data 字段

Advertising Data 的格式为：

```text
02 01 0A | NN 09 [BLE Name]
```

### 3.1 Flags

当前实际广播使用：

```text
02 01 0A
```

其中 `0x0A` 表示当前设备的 BLE Flags。协议表中的 `0x06` 是示例值；两个实测产品都使用 `0x0A`，因此它不是本次 APP 搜索差异的原因。

### 3.2 BLE 名称

```text
NN 09 [BLE Name]
```

- `NN`：`1 + 名称字节数`。
- `09`：Complete Local Name。
- `[BLE Name]`：UTF-8 名称，当前固件限制为最多 16 字节。

示例：

```text
11 09 5A 65 6E 63 68 64 20 43 61 73 65 20 30 30 30 33
      Z  e  n  c  h  d     C  a  s  e     0  0  0  3

名称：Zenchd Case 0003
名称长度：16 字节
Length：1 字节 AD Type + 16 字节名称 = 0x11
```

名称可能来自 VM 缓存，不一定与当前编译宏完全一致。修改 `BLE_LOCAL_NAME` 后，如果空口名称没有变化，需要检查或清除 `VM_RDX_BLE_NAME`。

实测已确认：在其他厂商数据完全保持可连接配置时，把名称从 `Zenchord Case` 恢复为最新格式 `Zenchd Case + SN 后四位`，APP 仍然可以搜索和连接。因此，这个 APP 当前不使用 BLE 名称作为扫描过滤条件。

## 4. Scan Response Data 字段

目前实测到两种 RDX Manufacturer Data 格式。

旧版基础格式共 23 字节，以 `16 FF` 开头：

```text
16 FF
+ PID[3]
+ MAC[6]
+ Id mark[6]
+ State[1]
+ Ability[4]
+ Protocol version[1]
```

新版扩展格式共 27 字节，以 `1A FF` 开头：

```text
1A FF
+ PID[3]
+ MAC[6]
+ Id mark[6]
+ State[1]
+ Ability[4]
+ Protocol version[1]
+ SKU[2]
+ Self mark[2]
```

当前工程默认使用新版扩展格式。已经找到的 PID 603 参考机使用旧版基础格式，并且可以正常连接 APP，说明 APP 同时兼容这两种长度。

### 4.1 新版扩展格式字节偏移表

偏移从 Scan Response Data 的第一个字节开始计算：

| 偏移 | 长度 | 字段 | 格式 | 示例 |
| ---: | ---: | --- | --- | --- |
| 0 | 1 | Length | 二进制 | `1A` |
| 1 | 1 | AD Type | 二进制 | `FF` |
| 2～4 | 3 | PID / 产品形态编码 | ASCII | `603` |
| 5～10 | 6 | BLE MAC | 二进制 | `78 78 35 9A 70 97` |
| 11～16 | 6 | Id mark / 厂商码 | ASCII | `ZENCHD` |
| 17 | 1 | State / 状态 | 位图 | `40` |
| 18～21 | 4 | Ability / 能力位 | 位图 | `22 00 00 00` |
| 22 | 1 | Protocol version | 二进制 | `17` |
| 23～24 | 2 | SKU / 产品型号 | ASCII | `E1` |
| 25～26 | 2 | Self mark / SDK 标识 | ASCII | `NV` |

`1A` 表示其后共有 26 字节：1 字节 `FF` 加 25 字节厂商数据。

旧版基础格式中，偏移 0～22 与上表前半部分相同，但在 Protocol version 后结束，不包含 SKU 和 Self mark。

### 4.2 PID / 产品形态编码

PID 是 RDX 对设备产品形态的编码，用来区分耳机本体、录音卡片、充电仓、录音 PIN 等不同形态。PID 不是具体的客户产品型号，也不是二进制整数；它在广播中固定使用 3 字节 ASCII 字符串表示。

```text
36 30 33 = "603"
36 30 32 = "602"
```

当前固件中的产品形态约定：

| PID | 产品形态 |
| --- | --- |
| `601` | 耳机本体 EP |
| `602` | 录音卡片 Record Card |
| `603` | 充电仓 Charge Case |
| `604` | 录音 PIN |

旧版协议表只明确列出了 `602`。如果 APP 支持的产品形态列表没有同步增加 `603`，即使广播格式正确，也可能被 APP 过滤。

### 4.3 BLE MAC

MAC 固定占 6 字节，每台设备不同。MAC 内容变化通常是正常现象，不应使用某个固定 MAC 作为通用扫描条件。

当前固件组包时会对控制器返回的 MAC 做字节反转，因此阅读日志时需要注意显示方向。

### 4.4 Id mark / 厂商码

Id mark 固定占 6 字节，以 ASCII 保存：

```text
5A 45 4E 43 48 44 = "ZENCHD"
4E 6F 74 74 61 48 = "NottaH"
```

协议表明确说明：APP 扫描时通过 Manufacturer Data 中的 Id mark 判断是否为有效设备。

因此，Id mark 是明确的扫描过滤字段。不同客户 APP 通常只识别自己配置的厂商码。

### 4.5 State / 状态

State 是 1 字节位图：

| Bit | 含义 |
| ---: | --- |
| bit7 | AI mode：`0` 为 TWS mode，`1` 为 AI mode |
| bit6 | Bound：`0` 为未绑定，`1` 为已绑定 |
| bit5～bit0 | 预留 |

常见值：

```text
00 = 未绑定
40 = 已绑定
80 = AI mode、未绑定
C0 = AI mode、已绑定
```

受控实验中，只把 State 从 `00` 改为 `40` 后 APP 仍然可以连接。因此，绑定状态不参与当前 APP 的扫描过滤。

### 4.6 Ability / 设备能力

Ability 固定占 4 字节。阅读时按照广播中的字节顺序，从第 1 字节到第 4 字节依次解析。

第 1 字节：

| Bit | 能力 |
| ---: | --- |
| bit7 | 本地存储 |
| bit6 | Wi-Fi AP |
| bit5 | 会议录音 |
| bit4 | 通话录音 |
| bit3 | 会议录音降噪 |
| bit2 | 经典蓝牙 |
| bit1 | RTC |
| bit0 | 多媒体录音 |

第 2 字节：

| Bit | 能力 |
| ---: | --- |
| bit7 | Left/Right 1V1 |
| bit6 | Wi-Fi AP V2 |
| bit5 | Child/Parent |
| bit4 | Network |
| bit3 | FlashNote / 闪记 |
| bit2 | Record Mark / 录音标记 |
| bit1 | 录音暂停/恢复 |
| bit0 | 预留 |

第 3、4 字节当前预留，默认为 `00 00`。

示例：

```text
22 00 00 00
```

第 1 字节 `0x22 = 0010 0010b`，表示支持：

- bit5：会议录音；
- bit1：RTC。

```text
FA 40 00 00
```

- 第 1 字节 `0xFA`：本地存储、Wi-Fi AP、会议录音、通话录音、会议录音降噪、RTC；
- 第 2 字节 `0x40`：Wi-Fi AP V2。

Ability 用于 APP 决定展示和启用哪些功能，不用于扫描过滤，因此反推实验跳过该字段。

### 4.7 Protocol version / 协议版本

协议版本固定占 1 字节，是二进制数，不是 ASCII 字符串。

```text
17 = 0x17 = 十进制 23
15 = 0x15 = 十进制 21
```

协议版本主要用于协议兼容和 OTA 校验。协议表没有明确说明它用于扫描过滤。

### 4.8 SKU / 产品型号

SKU 固定占 2 字节，以 ASCII 保存。固件代码中对应 `PRODUCT_TYPE`。

```text
45 31 = "E1"
4D 32 = "M2"
```

SKU 用于区分客户产品型号。APP 可能使用 `PID + Id mark + SKU` 判断具体产品。

### 4.9 Self mark / SDK 标识

Self mark 固定为：

```text
4E 56 = "NV"
```

协议表明确说明 APP 会使用 Self mark 过滤其他非 RDX SDK 设备。因此 `NV` 也是明确的扫描过滤字段。

但实测可连接的 PID 603 旧版广播在 Protocol version 后直接结束，并不携带 `NV`。这说明实际 APP 为旧格式保留了兼容分支，`NV` 不是所有历史产品都必须存在的字段；是否检查 `NV` 取决于 APP 进入了旧版还是新版解析流程。

### 4.10 Device color / 产品颜色

Excel 协议表定义了一个可选的尾部字段：

```text
Device color[1]
```

如果携带该字段，扫描响应应为 28 字节，开头 Length 为：

```text
1B FF
```

当前两个实测包都是 `1A FF`，没有携带 Device color，但其中一个产品可以正常连接 APP。因此，缺少 Device color 不是这两个包搜索结果不同的原因。

### 5.5 单变量反推实验记录

| 轮次 | 相对上一轮的变化 | Manufacturer Data 关键内容 | 结果 | 当前结论 |
| ---: | --- | --- | --- | --- |
| 0 | 当前工程原始配置 | `603 + ZENCHD + 40 + 22000000 + 17 + E1 + NV` | 不可连接 | 待反推 |
| 1 | 除 MAC 外，完全模拟可连接 PID 603 旧版产品 | `603 + NvEasy + 00 + 20000000 + 13` | 可以连接 | 模拟基线成立 |
| 2 | 只把名称从 `Zenchord Case` 恢复为 `Zenchd Case + SN 后四位` | Manufacturer Data 与轮次 1 相同 | 可以连接 | BLE 名称不参与当前 APP 的过滤 |
| 3 | 只把 Id mark 从 `NvEasy` 改为 `ZENCHD` | `603 + ZENCHD + 00 + 20000000 + 13` | 不可连接 | Id mark 参与过滤；PID 603 旧版分支接受 `NvEasy`，不接受 `ZENCHD` |

轮次 2 已确认名称不参与过滤，轮次 3 确认 Id mark 是决定字段之一，轮次 4 确认 State 不参与过滤。Ability 按协议用途确定为功能描述字段，同样跳过。反推实验暂时停止，最后一版已确认可连接的基线为：最新动态名称、`603 + NvEasy + 40 + 20000000 + 13`、旧版 `16 FF` 格式。

## 6. APP 扫描过滤规则

协议表规定的新版扫描过滤字段：

```text
Id mark + Self mark
```

- Id mark：识别客户或厂商，例如 `NvEasy`、`NottaH`、`ZENCHD`。
- Self mark：新版格式固定为 `NV`，识别 RDX SDK 设备。

实际 APP 还兼容没有 Self mark 的 `16 FF` 旧版格式。结合当前实测，APP 更可能根据格式版本和产品身份进入不同的白名单分支，例如：

```text
PID + Id mark + SKU + Self mark
```

目前已知结果：

```text
可连接：602 + NottaH + M2 + NV（新版 1A FF）
可连接：603 + NvEasy（旧版 16 FF）
不可连接：603 + ZENCHD（旧版 16 FF，其他字段与可连接包完全相同）
不可连接：603 + ZENCHD + E1 + NV（新版 1A FF）
不可连接：603 + NottaH + E1 + NV（新版 1A FF）
```

受控单变量实验已经确认：

- 保持 Manufacturer Data 不变，只修改 BLE 名称，仍可连接，因此名称已排除。
- 保持其他字段不变，只把 Id mark 从 `NvEasy` 改为 `ZENCHD`，立即变为不可连接，因此 Id mark 明确参与过滤。
- 恢复 `NvEasy` 后，只把 State 从 `00` 改为 `40`，仍可连接，因此 State 已排除。
- Ability 是功能能力声明，不用于扫描过滤，跳过该字段。

在没有 APP 源码的情况下，不能仅凭这些组合断定最终完整规则。当前反推暂停，尚未验证的字段保留为“未知”，不提前下结论。

## 7. 从 nRF RAW Data 手工拆包

nRF 中复制出来的 RAW Data 可能是一整串连续十六进制，例如：

```text
0x02010A11095A656E636864204361736520303030371AFF3630337878359A709B4E6F7474614840220000001745314E56
```

### 7.1 基本拆分规则

1. 删除开头的 `0x`、空格和换行；它们不属于广播数据。
2. 每两个十六进制字符表示 1 字节，例如 `1A` 是 1 字节。
3. 每个 AD Structure 的第 1 字节都是 `Length`，并且按十六进制读取。
4. 当前 AD Structure 实际占用的总字节数为 `Length + 1`，这个 `1` 是 Length 字节自身。
5. 下一段的起始偏移计算公式为：

```text
下一段偏移 = 当前段偏移 + 1 + Length
```

不要通过肉眼直接搜索固定内容来确定所有边界。BLE 允许增加或调整 AD Structure，应始终优先按照 Length 逐段向后解析。

### 7.2 用实际 RAW Data 逐段拆分

对上面的 RAW Data，从字节偏移 0 开始：

| 当前偏移 | Length | 本段总长度 | AD Type | 本段内容 | 下一段偏移 |
| ---: | ---: | ---: | ---: | --- | ---: |
| 0 | `02` = 2 | 3 字节 | `01` Flags | `02 01 0A` | 3 |
| 3 | `11` = 17 | 18 字节 | `09` Complete Local Name | `11 09` + 16 字节名称 | 21 |
| 21 | `1A` = 26 | 27 字节 | `FF` Manufacturer Data | `1A FF` + 25 字节厂商数据 | 48，结束 |

因此，原始长字符串首先被拆成三个完整的 AD Structure：

```text
第 1 段：Flags
02 01 0A

第 2 段：BLE 名称
11 09 5A 65 6E 63 68 64 20 43 61 73 65 20 30 30 30 37
      "Zenchd Case 0007"

第 3 段：RDX Manufacturer Data
1A FF 36 30 33 78 78 35 9A 70 9B 4E 6F 74 74 61 48 40 22 00 00 00 17 45 31 4E 56
```

在 RDX 当前设计中：

- `Flags + BLE 名称` 属于 Advertising Data；
- `Manufacturer Data` 属于 Scan Response Data。

如果 nRF 已经把 `Advertising Data` 和 `Scan Response` 分栏显示，则分别对每一栏使用相同的 Length 规则解析即可。

### 7.3 继续拆 RDX Manufacturer Data

确认 AD Type 为 `FF` 后，先读取 Length 判断版本：

```text
16 FF = 旧版基础格式，在 Version 后结束
1A FF = 新版扩展格式，Version 后还有 SKU 和 Self mark
```

新版扩展格式从 `FF` 后按以下固定字段宽度切分：

```text
3 | 6 | 6 | 1 | 4 | 1 | 2 | 2
PID MAC Id State Ability Ver SKU Self
```

实际数据对齐如下：

```text
1A FF
| 36 30 33
| 78 78 35 9A 70 9B
| 4E 6F 74 74 61 48
| 40
| 22 00 00 00
| 17
| 45 31
| 4E 56
```

解析结果：

| 字段 | HEX | 解析值 |
| --- | --- | --- |
| PID / 产品形态 | `36 30 33` | ASCII `603`，充电仓 |
| MAC | `78 78 35 9A 70 9B` | 6 字节设备 MAC 字段 |
| Id mark | `4E 6F 74 74 61 48` | ASCII `NottaH` |
| State | `40` | 已绑定 |
| Ability | `22 00 00 00` | 会议录音 + RTC |
| Protocol version | `17` | `0x17`，十进制 23 |
| SKU | `45 31` | ASCII `E1` |
| Self mark | `4E 56` | ASCII `NV` |

以后可以直接套用下面的模板：

```text
02 01 [Flags]
NN 09 [BLE Name，NN - 1 字节]
16/1A FF
[PID 3]
[MAC 6]
[Id mark 6]
[State 1]
[Ability 4]
[Version 1]
[SKU 2，仅1A新版]
[Self mark 2，仅1A新版]
```

### 7.4 快速自检

- 去掉 `0x` 后，十六进制字符总数必须是偶数。
- 每段数据长度必须等于 `Length + 1`。
- 名称字节数必须等于名称段的 `Length - 1`。
- RDX 旧版厂商段为 23 字节，以 `16 FF` 开头；当前无 Device color 的新版厂商段为 27 字节，以 `1A FF` 开头。
- 如果末尾仍有未解析字节，优先检查 Length、可选字段或是否还拼接了其他 AD Structure。

## 8. 广播问题排查清单

当 APP 搜索不到设备时，按以下顺序检查：

1. 确认抓到的是 Advertising Data 和 Scan Response Data 的完整数据。
2. 确认每个 AD Structure 的 Length 正确。
3. 确认 Scan Response Data 是已知的 `16 FF` 旧版或 `1A FF` 新版格式，字段没有错位。
4. 如果是 `1A FF` 新版格式，确认 Self mark 为 `NV`。
5. 确认 Id mark 是目标 APP 支持的厂商码。
6. 确认 PID 产品形态和 SKU 客户型号已加入 APP 的产品白名单。
7. State 已通过单变量实验排除，不参与当前 APP 的扫描过滤。
8. 检查协议版本是否在 APP 支持范围内。
9. Ability 不参与扫描过滤；连接后功能异常时再检查其能力位是否正确。
10. BLE 名称已通过单变量实验排除；仅在显示名称异常时检查 VM 中的旧值。
11. 修改字段时每次只改变一个变量，并保存每轮实际抓包数据。

## 9. 结论

### 9.1 已确认

- APP 至少支持两种已知产品组合：`602 + NottaH + M2 + NV` 新版格式，以及 `603 + NvEasy` 旧版格式。
- PID `603` 有可连接实机，因此不能把问题简单归因于“APP 不支持 603”。但受控实验中 PID 始终保持 `603`，尚不能据此认定 APP 完全不检查 PID。
- BLE 名称不参与当前 APP 的过滤。名称从 `Zenchord Case` 改为 `Zenchd Case + SN 后四位` 后仍可连接。
- Id mark 明确参与 APP 过滤。在其他字段完全相同时，`NvEasy` 可以连接，改成 `ZENCHD` 后无法连接。
- State 不参与过滤。State 从 `00` 改为 `40` 后仍可连接。
- Ability 只描述设备功能，不参与扫描过滤。
- MAC 是设备动态身份，不能作为跨设备的固定比较条件。
- APP 能处理已知的 `16 FF` 旧版包和 `1A FF` 新版包，但尚未把“格式长度”作为单变量独立验证。

### 9.2 尚未确认

- Protocol version 是否参与过滤。
- 新版格式中的 SKU 是否参与产品白名单匹配。
- 新版格式中的 Self mark 是否参与过滤；旧版可连接包没有 Self mark，说明它不是所有历史产品的必选字段。
- PID 是否作为白名单条件之一；目前只能确认 `603` 是受支持的产品形态。
- APP 最终使用的是单独 Id mark 白名单，还是 `PID + Id mark + SKU + 格式版本` 的组合白名单。

### 9.3 当前保留的已验证基线

反推实验暂时停止。源码恢复到最后一版已确认可以连接的广播配置：

```text
BLE Name：Zenchd Case + SN 后四位
PID：603
Id mark：NvEasy
State：40
Ability：20 00 00 00
Protocol version：13
格式：16 FF 旧版基础格式
SKU：不携带
Self mark：不携带
MAC：使用设备真实 MAC
```

后续恢复反推时，应继续从这份已验证基线出发，每次只修改一个尚未确认的字段。实际抓包是最终依据，不应只根据编译宏推断空口数据。
