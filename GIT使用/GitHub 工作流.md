# 8. GitHub 工作流

> 本文以 GitHub Actions 为例，先解释各类自动化工作流的通用概念，再通过实际遇到的设置理解这些原理。
> 章节分为“通用原理（一至七）”与“实战案例（八）”。实战按“问题 → 作用与场景 → 本项目选择 → 可迁移经验”组织，只补充真正遇到的问题，不扩写成全部设置的百科或执行日志。建议与已验证状态分开记录，不存凭据。团队开发规范与发布看 7 号；CPA 升级/回滚看 6 号。

## 一、工作流到底是什么？

**工作流，就是把“什么时候开始、按什么顺序做什么、遇到问题怎么办”写成一套明确的流程。**

原来由人记住并逐条执行的步骤，可以交给机器执行。例如：

```text
收到发布指令
→ 获取指定版本的源码
→ 测试、编译
→ 打包成软件或镜像
→ 上传到发布仓库
→ 通知结果
```

可以把它理解为一条生产线：流程定义是工序单，执行机器是工位，输入是原料，输出是成品。平台负责按规则安排执行，并记录每道工序的结果。

GitHub Actions、GitLab CI/CD、Jenkins 等都能实现这类自动化。它们的界面、配置语法和叫法不同，但核心理念相通。工作流也不限于软件开发，审批、数据处理、定时报告等都可以用同样的方法组织。

## 二、一套工作流通常包含什么？

| 通用概念 | 通俗解释 | 例子 |
|---|---|---|
| 触发条件 | 什么时候开始 | 提交代码、到达时间、点击按钮 |
| 输入 | 这次处理什么 | 某个源码版本、一份数据、目标环境 |
| 任务与步骤 | 具体做哪些事情 | 测试、编译、打包、上传 |
| 依赖与条件 | 哪些先做，什么情况才继续 | 测试通过后才允许发布 |
| 执行环境 | 谁来干活、需要什么工具 | 装有编译器和 Docker 的机器 |
| 输出 | 最后得到什么 | 镜像、安装包、报告 |
| 结果与记录 | 做成没有，哪里出了问题 | 成功通知、失败日志 |

**自动化不等于自动开始。**人手动点击一次按钮，随后机器自动完成整套流程，同样是自动化。

本项目现已决定采用自动触发：dev 完整 CI 和 dev → main 发布 PR 检查通过、负责人合并后，main 自动打包并上传团队镜像。版本在 PR 中确定：官方基线和团队版本独立递进，纯官方同步保持团队版本，团队定制变化才递增团队版本；CI 检查新的版本组合及禁止倒退、覆盖的约束。无需额外手动启动发布；生产服务器部署仍按 7 号 SOP 执行。具体配置与实际验证状态见仓库的 GitHub Actions 工作流适配文档。

“流程”与“某次运行”也不同：流程是可以反复使用的配方；每次运行是按这份配方做的一次产品，有各自的输入、日志和结果。

## 三、它不只是从头到尾执行命令

简单流程是一条直线，复杂流程还可以有：

- **顺序执行**：先编译，再打包；后一步依赖前一步的结果。
- **并行执行**：同时测试不同系统，或同时构建不同架构的镜像。
- **条件分支**：普通代码提交只测试，发布版本才打包上传。
- **人工关卡**：机器准备好发布包后，等待负责人批准上线。
- **失败处理**：停止后续发布、保存日志、通知负责人；适合重试的步骤才重试。

因此，工作流平台不只是“运行一个脚本”，还负责安排任务、传递结果、控制依赖、管理执行状态。脚本通常负责某个具体任务，工作流把这些任务组织起来。

## 四、为什么要用它？

最重要的价值不是“完全不用人”，而是**把重复工作标准化**：

1. **减少遗漏**：每次都执行约定的检查，不靠人记住所有命令。
2. **提高一致性**：用明确的源码、工具和配置构建，减少“我电脑上可以”的差异。
3. **尽早发现问题**：提交代码后就检查，不等到上线才发现错误。
4. **方便追溯**：知道哪个版本由谁触发、经过哪些步骤、生成了什么。
5. **节省重复劳动**：人关注设计和判断，机器负责反复执行。

前提是流程本身正确。错误流程自动执行，只会更快、更一致地重复错误。相同源码也不必然生成完全相同的产物，还需要控制依赖、工具版本和其他构建输入。

## 五、软件开发中的 CI/CD 是什么？

它们是工作流在软件开发中的常见用法，不是另一种神秘技术。

| 概念 | 核心含义 |
|---|---|
| CI：持续集成 | 频繁把代码变更集成起来，并通过自动构建和测试尽早发现问题 |
| Continuous Delivery：持续交付 | 将变更准备成经过验证、可以发布的产物；生产上线仍可由人批准 |
| Continuous Deployment：持续部署 | 满足检查条件后，进一步自动部署到生产 |

后两者都可能缩写为 CD，要看上下文。**使用 CI/CD，并不代表必须自动上线。**完全可以自动测试、自动打包，但生产部署保留人工确认。

## 六、以镜像发布为例

```text
选定并审核源码版本
        ↓
触发构建流程
        ↓
测试 → 编译 → 打包镜像
        ↓
上传镜像仓库，记录版本和内容标识
        ↓
核验发布产物
        ↓
人工批准 + 部署流程
        ↓
服务器运行新镜像，检查真实服务
```

这里要分清三个动作：

- **构建**：把源码加工成可运行的东西，相当于制作安装包。
- **发布**：把产物放到可获取的位置，相当于把安装包上架。
- **部署**：让目标机器使用该产物提供服务，相当于安装并启动。

三者可以串成一条流程，也可以分开。**镜像上传成功，不等于服务器已经升级；流程显示成功，也只证明配置的步骤通过了，不代表未检查的业务一定正常。**

## 七、自动化应该保留哪些边界？

- **人决定目标，机器执行规则**：版本是否值得升级、风险是否可接受，不能只靠“任务运行成功”来判断。
- **权限只给够用的**：测试代码不需要生产管理权限；打包发布也不必持有服务器登录钥匙。
- **失败要可见、后果要可控**：设定停止条件、超时和通知。重试上传与重试扣款的后果不同，不能无脑重跑。
- **回滚不是自动附送的**：流程中途失败可能已经改动外部系统；恢复、补偿和数据库回滚都要事先设计。
- **重要产物要可追溯**：记录源码、构建输入和产物标识，让测试和部署使用同一份经过核验的产物。

## 八、实战案例：把原理对应到真实设置

### 实战 1：给工作流选择可用的工具来源

**遇到的问题：**在团队仓库 `Settings → Actions → General` 中，Actions permissions 的四个选项该怎么选？最下面的 SHA 勾选项又管什么？

先记住一个类比：**工作流是生产线，Action 是拿来使用的工具，可复用工作流是一整段现成生产线。这里是在决定“允许向哪些供应商借工具”，不是决定“谁能进我们的仓库”。**

例如 `actions/checkout` 是 GitHub 提供的源码获取工具；Docker 提供的 Action 可以负责登录镜像仓库、构建镜像。它们的代码会参与执行，所以来源需要管理。

#### 四个互斥选项：从开放使用到来源白名单

| 页面选项 | 作用（通俗理解） | 通常适用于什么场景 |
|---|---|---|
| **Allow all actions and reusable workflows** | 不限制作者来源，允许引用各方的工具和可复用流程；私有组件仍需要访问权限 | 个人项目、小团队起步、探索流程时，减少白名单配置障碍；仍须审核实际引用的代码 |
| **Disable actions** | 关闭本仓库的工作流运行能力 | 项目不使用自动化，或需要停止后续自动化执行、排查风险；不会停止已经部署的生产服务 |
| **Allow HK-bruc1 actions and reusable workflows** | 只允许 HK-bruc1 名下仓库定义的工具和可复用流程 | 已有完整内部工具库、不允许直接引用外部组件的团队；不是“只允许 HK-bruc1 这个人点运行” |
| **Allow HK-bruc1, and select non-HK-bruc1, actions and reusable workflows** | 自家的可用，外部的必须进入允许名单 | 正式流程已稳定、希望限制供应链来源的项目；可只允许实际需要的 GitHub、Docker 等组件 |

**容易误选的地方：**第三项连 `actions/checkout` 都会挡住，因为它属于 `actions`，不是 `HK-bruc1`。第四项才是“自己的 + 批准过的外部工具”。选择第四项后，可进一步允许 GitHub 发布的组件、经验证发布者的组件或精确指定的仓库；发布者被验证不等于代码绝对安全。

选择 Allow all 不会公开仓库，也不会自动授予外人访问权或工具写权限。反过来，来源白名单也不能拦住所有风险：流程中直接运行的脚本、下载命令和软件依赖仍需要审核。

#### 独立勾选项：锁定具体哪一份工具

**Require actions to be pinned to a full-length commit SHA**：要求引用的 Action 固定到完整提交 SHA，包括 GitHub 和自己账号提供的 Action。

**易混淆点：这里锁定的是 Action 工具的代码提交，不是我们准备发布的 FelixApi 源码提交。**完整 commit SHA 确实标识 Git 历史中的一个确切提交，但必须先问“这是哪个仓库、哪个对象的提交？”

| 标识 | 锚定对象 | 由哪里决定 |
|---|---|---|
| Action 的完整 commit SHA | 获取源码、构建镜像等工具自身的某个提交 | 工作流引用工具时指定；本页面开关强制此类引用固定 SHA |
| 团队源码的完整 commit SHA | 本次要编译发布的 FelixApi 源码提交 | 发布流程另外指定和验证；本页面开关不会自动锁定它 |
| 镜像 digest | 构建出的实际镜像内容或多架构索引 | 构建发布后获取并核验；不是 Git 提交哈希 |

例如：

```text
获取源码的 Action → 使用工具仓库的提交 A
需要发布的 FelixApi 源码 → 使用团队仓库的提交 B
构建镜像的 Action → 使用另一工具仓库的提交 C
最终发布的镜像 → 记录镜像 digest D
```

A、B、C 都可以是 Git commit SHA，但含义不同；D 是产物的内容标识。**本开关约束 A、C 这类工具引用，不会替我们选定 B，也不会生成或固定 D。**发布流程需要将源码提交 B 与实际产物 D 对应记录；仅固定源码提交，也不能保证依赖和构建环境不同的两次构建得到同一 digest。

一句话区分：**Action SHA 锁定“用哪一份工具”，源码 SHA 锁定“加工哪一份源码”，镜像 digest 锁定“最终部署哪一份产物”。**

- **只写版本标签**：像指定某个型号，标签可能被维护者移动到另一份代码。
- **写完整 SHA**：锁定具体的一份代码，避免标签变化使下次执行悄悄换了工具。

它适合重视构建可追溯和供应链安全的流程，尤其是能读取凭据、发布产物的任务。代价是升级工具时要明确更换 SHA 并审核；锁定旧版本也不意味着可以永远不更新。

**来源白名单回答“用谁的工具”，SHA 回答“用这个工具的哪一份代码”。两者可以同时使用，不能互相替代。**SHA 固定不证明代码安全，也不自动锁定脚本下载的其他依赖。GitHub 当前这项强制要求针对 Action，可复用工作流仍可按 tag 引用，不应理解为所有依赖都已锁定。

#### 本项目当前建议与注意事项

1. 起步阶段选择 **Allow all actions and reusable workflows**，因为团队发布流程的依赖清单还未定稿。
2. 勾选 **Require actions to be pinned to a full-length commit SHA**，要求团队工作流从一开始就固定工具代码。
3. 点击本区块 **Save**。这只是保存规则，不会触发镜像构建或生产部署。
4. 团队工作流定稿后，从实际引用中整理白名单，再收紧到第四项；不是长期无条件信任所有来源。

**已知兼容性影响【源码实证】：**此前核对的团队提交 `97c040d111381d58d1fecec1e2ad29099a7655bc` 中，继承的 `docker-build.yml` 有 cosign 安装步骤引用 `@v3`，并未固定完整 SHA。启用限制后此类引用会不合规，需要先适配；不能因此直接运行旧工作流或给它补上无关凭据。

**状态边界：以上是建议，尚未读回验证网页选中项是否已保存。**工作流代码之后可能变化，执行前应重新核对。

#### 从这次实战带走的通用经验

无论换到哪个平台，都可以依次问：

```text
来源：允许使用谁提供的组件？
版本：有没有锁定经过审核的代码？
权限：运行时究竟能读写什么？
触发：什么时候运行，谁能批准？
```

本案例只处理前两项。不要把“允许使用外部组件”误认为“给它所有权限”，也不要把“组件版本已锁定”误认为“流程必然安全”。

参考：[GitHub 官方 Actions 仓库设置说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)。

### 实战 2：90 天保留期——从“镜像会过期吗”理解存储与运行

#### 最初的理解与问题

看到 **Artifact and log retention：90 days**，最初容易理解成：镜像如果连续 90 天没有更新，就会自动删除。

进一步的问题是：如果不是这样，镜像是否永远保存？谁提供物理存储、谁承担费用？镜像既然能被远端拉取，是不是也运行在 GitHub 上？

#### 第一次纠正：保留期管什么？

这个选项管理 **Actions 的运行日志和 Artifact 附件**，不是 GHCR 镜像的生命周期。

| 对象 | 通俗含义 | 是否受此设置控制 |
|---|---|---|
| Log | 获取源码、编译、测试、构建、上传等步骤的文字记录 | 是 |
| Actions Artifact | 工作流明确上传到 Actions、供下载或后续任务使用的文件，例如测试报告、安装包 | 是 |
| GHCR 中的镜像 | 推送到 `ghcr.io` 镜像仓库的产物 | 否 |
| VPS 上下载的镜像和运行数据 | 服务器自己的磁盘内容 | 否 |

**看存放位置，不只看文件内容。**如果把镜像导出为 `.tar` 并上传为 Actions Artifact，这个附件也受保留期约束；同一镜像推送到 GHCR 的那份则不受影响。

90 天按日志或附件创建后的保留时间理解，**不是“90 天不更新才删除”**。新运行产生新记录，不会自动为旧记录续期。修改保留设置只影响之后创建的对象，不追溯修改已有对象。当前私有仓库页面允许最多 400 天，但上限不是建议值。

#### 第二次纠正：镜像存放和服务运行是两回事

按我们计划采用的 GitHub 托管构建方案：

```text
GitHub 团队仓库：保存源码
        ↓ 获取指定提交
GitHub Actions 运行机器：编译、测试、构建
        ↓ 上传产物
GHCR 镜像仓库：保存镜像，供有权限的机器下载
        ↓ 拉取镜像
我们的 VPS：保存下载的镜像，启动容器提供服务
```

类比：**源码是配方，构建机器是工厂，GHCR 是安装包下载站，VPS 是下载安装包并运行软件的电脑。**

GitHub 提供 GHCR 的物理存储，但不会因此替我们运行 New API 业务。VPS 下载镜像后，占用自己的磁盘；容器运行时消耗 VPS 的 CPU、内存等资源。镜像是静态产物，真正运行的是根据它创建的容器。

我们本地也有源码，但 GitHub Actions 可以直接从团队仓库获取源码，在 GitHub 托管机器上构建，不要求 Mac 一直开着。本机手动构建的日志，也不会自动由这个网页设置管理。

#### 第三次纠正：谁付费，是否永久保存？

这三类资源分开看：

| 资源 | 谁提供 | 费用与责任 |
|---|---|---|
| 托管构建机器 | GitHub | 私有仓库受 Actions 免费额度与超额计费规则约束 |
| GHCR 镜像存储和下载带宽 | GitHub | 当前官方政策为免费，不能推断为永久免费 |
| 生产计算和磁盘资源 | VPS 服务商 | 我们支付服务器费用，并管理磁盘与运行数据 |

GitHub 当前说明：Container registry 的镜像存储和带宽免费；若政策调整，至少提前一个月通知。**这是 GHCR 的当前政策，不应套用到所有 GitHub Packages 类型或其他镜像仓库。**执行构建是否花钱，与保存镜像是否花钱，是不同问题。

“不受 90 天设置控制”也不等于“保证永远保存”。管理员删除、团队清理任务、平台政策与账号状态都可能影响可用性。关键发布产物与发布记录需要有备份方案，不能把唯一一份远程镜像当作永久存档。

#### 本项目怎么选择？

- 此项先保留 **90 天**，便于回查构建问题，不因为上限是 400 天就全部留到上限。
- 源码提交、镜像 digest、测试和验收结论另存长期发布记录，不只放在会过期的日志中。
- 镜像清理与服务器回滚资产保留单独管理，生产安全规则仍以 6 号为准。
- 以上为建议，尚未核验用户是否保存了网页配置；本案例没有执行镜像删除或生产变更。

#### 最后形成的通用理解

从“镜像多久不用就会消失”的误解，转变为先问四件事：

1. **对象是什么？**源码、日志、附件、镜像还是运行数据？
2. **存在哪里？**代码仓库、自动化平台、镜像仓库还是生产服务器？
3. **谁管理生命周期？**哪一项保留设置、清理策略或人工操作？
4. **谁提供资源、如何计费？**构建计算、产物存储和生产运行分开核算。

**一句话记住：90 天管的是流水线的记录和附件，不是下载站中的镜像，更不是服务器上的业务。**

参考：[GitHub Actions 仓库设置与保留规则](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)、[GitHub Packages / GHCR 计费说明](https://docs.github.com/en/billing/concepts/product-billing/github-packages)。计费政策可能变化，实际使用时重新核对。

### 实战 3：Fork PR——“接受流程文件”还是“允许执行流程”？

#### 最初的理解

看到 **Fork pull request workflows → Run workflows from fork pull requests**，最初的猜测是：这个选项决定是否接受 Fork 提交的 PR 中带来的新工作流。又因为团队仓库是私有的，认为没有人能 Fork，所以无需勾选。

**不勾选的选择适合我们，但这两个理由需要分别纠正。**

#### 第一次纠正：管理执行，不是决定接受哪些文件

这个选项决定：**是否允许来自 Fork 仓库的 PR 运行工作流。**它是执行许可；具体是否触发，还要符合工作流定义的事件、分支和路径等条件。

```text
成员在允许的情况下 Fork 团队仓库
→ 在自己的 Fork 修改代码
→ 向团队仓库提交 PR
→ 检查是否允许 Fork PR 运行工作流，以及是否满足触发条件
→ 运行测试、编译等检查
→ 人工审核后，另行决定是否合并 PR
```

这里不是“对方给了我们一套新流程，我们接不接受”，而是“对方提交了改动，我们是否允许自动化检查为这个 PR 执行”。

| 情况 | 实际含义 |
|---|---|
| PR 只修改业务代码，没有新增 YAML | 仍可能触发已有的测试工作流 |
| PR 新增或修改工作流文件 | 是否接受这些文件，要靠代码审核与合并决定；不是这个开关在批准 |
| 关闭本选项 | 不允许这一类 Fork PR 工作流运行，不等于禁止提交 PR 或禁止人工合并 |
| 开启本选项 | 提供执行许可，不代表每个 PR 都无条件运行，更不代表自动接受或合并 PR |

**关键区别：允许执行流程 ≠ 接受流程文件 ≠ 合并业务代码。**不要将这三件事合成一个“接受 PR”的概念。工作流文件变化本身也是需要审核的代码，运行前后都不能省略相应的安全判断。

#### 第二次纠正：私有仓库也可能有 Fork

私有表示陌生人不能随意访问，并不表示所有人都无法 Fork。**有访问权限的人，在所有者允许和平台策略支持的情况下，可以 Fork 私有仓库。**本次没有核验本仓库具体的 Fork 许可，不能声称已禁止或已开放。

因此要分清三个问题：谁能访问仓库、是否允许 Fork、Fork PR 是否允许运行工作流。它们不是同一个设置。

#### 为什么页面提醒“只读 Token”？

页面说开启后，Fork 维护者可能利用对源仓库具有只读权限的 Token。原因是测试、编译可能执行 PR 中的代码，不是只查看文字差异。

GitHub 对此类私有仓库 Fork PR 的默认规则是：使用只读 `GITHUB_TOKEN`，不提供 Secrets；额外的写 Token 或 Secrets 开放选项属于另一层高风险授权，不能顺手开启。

只读降低了修改仓库的风险，**不等于没有信息泄露风险**：不可信程序仍可能读取并外传其有权访问的内容，也会消耗执行资源。因此，这个选项涉及“是否让另一个仓库提供的代码进入我们的执行环境”，而不只是方便自动测试。

#### 本项目的选择与正确理由

**建议不勾选**，因为团队当前采用同仓库任务分支协作：

```text
FelixApi 内部：dev → feat/某项功能 → PR → dev
```

成员不需要通过另一个 Fork 仓库贡献代码，所以暂时没有开放 Fork PR 工作流的必要。关闭这一项不会因此禁止同仓库任务分支 PR 的自动测试，具体运行条件仍由工作流定义。

准确理由是“我们不用 Fork 协作”，不是“私有仓库不可能被 Fork”。如果以后改用 Fork 协作，再一起评估执行许可、人工批准、Token 和 Secrets 边界。**目前只记录建议，尚未核验网页是否保存。**

#### 从误解到通用原理

这次理解的变化是：

```text
最初：是否接受 PR 带来的新工作流？
纠正：是否允许来自 Fork 的 PR 执行工作流？
进一步：允许执行只是前提，还需要满足触发条件。
最终：执行、访问、审核、合并是不同层面的权限与决定。
```

在其他自动化平台上也一样：**允许别人提交材料，不等于允许执行材料中的程序；允许程序执行，也不等于审核通过或正式采纳。**

参考：[GitHub 私有仓库 Fork PR 工作流设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#enabling-workflows-for-forks-of-private-repositories)、[Fork 的访问与权限条件](https://docs.github.com/en/pull-requests/reference/forks)。

### 实战 4：Workflow permissions——机器人没有智能，为什么还能修改文件、创建 PR？

#### 从页面问题出发：是不是允许工作流修改源码？

**Workflow permissions** 配置的是工作流使用的 `GITHUB_TOKEN` 的默认权限。可以把它理解为 GitHub 自动发给任务的临时工作证，不是 AI 能力，也不是我们的账号密码。

“能不能改源码”只猜中了部分含义，还必须区分两种修改：

- **修改构建机器上的文件**：下载源码后写入版本号、生成文件、编译打包，不需要 GitHub 仓库写权限。
- **把修改提交并推回 GitHub**：需要相应的仓库写权限，并遵守分支规则。

本设置还涉及软件包、PR 等 API 操作，不只管源码。它控制这张 Token 的权限；若工作流另外持有其他凭据，还必须单独审查那些凭据的权限。

#### 页面选项如何选择？

| 选项 | 作用与应用场景 | 本项目建议 |
|---|---|---|
| **Read and write permissions** | 默认给 Token 较宽的仓库读写权限，适用于需要自动写入的任务；不等于整个账号的无限权限 | 不选；不让测试、构建任务默认拥有不必要的写权限 |
| **Read repository contents and packages permissions** | 默认只读代码与软件包，适合获取源码、测试和编译 | 选择；发布任务再单独声明所需权限 |
| **Allow GitHub Actions to create and approve pull requests** | 允许使用 GITHUB_TOKEN 的工作流在具备相应权限时创建 PR、提交批准意见 | 当前不勾选；我们的镜像发布不需要创建或批准 PR |

“默认只读”不是不可提升的上限。工作流可在平台和上级策略允许的范围内，为特定 Job 显式申请权限。例如镜像发布需要：

```yaml
# 仅为权限片段，不是完整工作流
permissions:
  contents: read
  packages: write
```

这表示“能读源码、能发布有权限的包”，不是“能修改源码”。同理，自动创建 PR 通常需要推送分支的代码写权限、PR 写权限以及相关设置允许；勾选页面开关本身不会创建 PR，也不保证能绕过分支规则。**批准 PR 与合并 PR 仍是不同动作。**

#### 延伸疑问：工作流不是 AI，怎么能创建 PR？

这里需要把“自动修改”与“自主推理”分开。普通程序可以按明确规则修改文件，也能通过 GitHub API 创建 PR；创建 PR 是一次接口操作，不要求程序理解业务。

最常见的例子之一是**定期更新外部依赖**：

```text
预先制定规则：定期检查，只更新允许范围内的依赖
→ Actions 到时间启动
→ 依赖更新工具比较可用版本
→ 修改依赖声明和锁定文件
→ 运行测试与构建检查
→ 将实际修改提交到专用任务分支
→ 调用 GitHub API 创建指向 dev 的 PR
→ 人工审核是否合并
```

PR 的标题、更新列表和检查结果可以由模板生成，不需要 AI 撰写。没有符合规则的变化就结束；已有同类 PR 时，流程应避免重复创建。

这不是“发现新版就发一个空 PR 通知”。**PR 应包含实际文件差异**，例如依赖声明与锁定文件的变更。合并后，下次安装或构建才会按新记录获取依赖，通常不是把外部库的整份源码合进项目。

“更新版本更高”也不自动意味着应该采纳：可以只接受补丁更新、排除指定依赖或延后重大升级。测试通过才创建普通 PR，还是失败时创建草稿 PR 附上日志，也需要事先定义。Dependabot 是典型的依赖更新机器人，但不是 GitHub Actions 本身；Actions 也可以调度其他更新工具实现这类流程。

#### 固定流程为什么会失败，会自己修复吗？

固定的是步骤，不是成功结果。源码编译错误、测试未通过、依赖下载失败、环境不兼容、资源不足、上传权限缺失，都可能导致任务失败。**镜像已经构建成功但上传被拒绝，是发布失败，不应因此随便修改业务代码。**

普通工作流按规则停止、保存日志并通知；只有预先配置了对应工具，才会重试下载、自动格式化或执行其他已知修复。它不会因为构建失败，就自行研究业务 Bug 并提出正确解决方案。

如果另行接入 AI Agent，才可能形成“分析日志 → 尝试修复 → 测试 → 创建 PR”的流程；此时 Actions 负责调度，Agent 负责分析，审核仍应保留。**我们当前没有配置这种 AI 自动修复流程。**

#### 本次配置与最终理解

当前镜像发布流程只需获取审核源码、检查、构建和上传产物，不需要自动改业务代码或创建 PR。因此：

1. 选择 **Read repository contents and packages permissions**。
2. 不勾选 **Allow GitHub Actions to create and approve pull requests**。
3. 保存本区块；之后在发布 Job 单独配置 `packages: write`。

以上是推荐值，尚未读回验证网页保存状态。以后真要做自动依赖更新，再为该任务设计分支、权限和人工审核规则，不为假想用途提前开放权限。

**从这次讨论带走的原则：权限决定“允许做什么”，流程决定“实际做什么”，工具决定“能完成什么”；是否具备 AI 推理能力，是另外一个问题。**自动创建 PR 是按规则提出修改申请，不代表自动批准，更不代表机器人会自主修 Bug。

参考：[GitHub 工作流 Token 默认权限设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)、[工作流权限语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)。

### 实战 5：Access——借进来与借出去

**问题：**General 最后的 Access 是否控制仓库公开、成员访问，或者服务器拉取镜像？

不是。这里控制的是**其他仓库的 Actions 能否通过该共享机制使用本私有仓库里的 Action 和可复用工作流**。

| 选项 | 作用与场景 |
|---|---|
| **Not accessible** | 不向其他仓库开放这类组件复用；适合只为自身提供流程的业务仓库 |
| **Accessible from repositories owned by the user 'HK-bruc1'** | 允许同账号下其他私有仓库调用这里的组件；适合多个项目共用构建、测试或发布流程 |

例如多个服务都要构建镜像，可以把共同流程放在一个专门的工作流仓库，其他项目调用它，避免每个项目复制维护。提供方需要配置共享访问，可复用工作流也需要声明相应调用入口；开放 Access 不会自动把普通工作流变成可调用流程。

用方向理解最清楚：**Actions permissions 管“我们能借谁的工具”，Access 管“谁能借我们的工具”。**后者不是一般的代码访问或写入授权，也不是 GHCR 镜像读取权限。共享私有组件会扩大信任边界，调用方协作者可能通过运行与日志间接接触共享内容。

**本项目选择：Not accessible。**目前 FelixApi 是业务仓库，没有向其他项目提供公共流程的需求。这不妨碍本仓库执行工作流、使用允许的外部 Action、发布 GHCR 镜像，也不妨碍服务器持正确凭据拉取镜像。

### General 配置阶段状态

用户已表示完成 General 各项配置；这是**用户报告完成，尚未由助手读回核验**，不是自动化实测通过。General 配好只代表执行规则准备完成，不代表团队发布工作流、镜像构建或生产部署已经完成。后续仍需审核并适配团队 YAML，而不是直接运行继承的官方发布流程。

### 实战 6：Runners 与 OIDC——执行位置与身份认证是两回事

#### Runners：到底是哪台机器在干活？

Runner 是实际执行工作流的机器，负责获取源码、测试、编译和打包。它不是流程本身，也不是镜像仓库。

| 选择 | 含义与场景 | 本项目当前方案 |
|---|---|---|
| GitHub 托管 Runner | GitHub 分配执行环境，适合通用构建，不用自己维护机器 | 首期使用；在工作流中选择合适环境，不必添加自建 Runner |
| 自建 Runner | 自己的电脑、云服务器或专用构建机器接收并执行任务；适合内网访问、特殊硬件或定制环境 | 暂不配置；尤其不把生产 VPS 当构建机器 |

自建不等于必须使用容器，可以直接运行在机器上，也可以设计为容器化执行。无论采用哪种，都要考虑工具安装、隔离、资源、清理和不可信代码的风险。

“使用 GitHub 免费资源”还需分清：托管构建受免费额度与计费规则约束；GHCR 镜像存储与带宽是当前免费政策，不能推断为所有资源无限免费。镜像发布后保存到 GHCR，并不表示运行机器永久保存了它。

#### OIDC：不是另一台机器，而是证明身份的方法

最初容易把 OIDC 理解为“对外的 GitHub Token”。这个类比能帮助入门，但两者不是同一种东西：

| 概念 | 准确含义 | 通俗类比 |
|---|---|---|
| OIDC | 一种身份认证协议；工作流可通过它取得签名的身份令牌 | 出示可信身份证明的机制 |
| OIDC 身份令牌 | 证明某个任务来自哪个仓库、工作流和运行上下文等 | 身份证明 |
| GITHUB_TOKEN | GitHub 自动提供的访问令牌，按权限访问 GitHub 仓库、Packages、PR 等资源 | GitHub 临时工作证 |

典型的外部云访问流程是：

```text
先在外部云平台配置受信任的仓库、工作流或发布条件
→ 工作流申请 GitHub 签发的 OIDC 身份令牌
→ 云平台核验身份是否符合信任规则
→ 云平台发放自己的短期访问凭据
→ 工作流用该凭据操作云资源
```

**GitHub 证明身份，目标服务决定权限。**相较于在 Secrets 中长期保存云平台密钥，这种方式可以减少长期密钥的保管与轮换负担；但不是勾选一个设置就能访问任意云服务。目标服务必须支持相应机制，且双方配置正确。

#### 关键纠正：外部 Runner 不代表必须配置 OIDC

“机器来自外部，是不是要改 OIDC？”混淆了执行地点与认证目标。自建 Runner 执行的仍是 GitHub Actions 任务，也可以按规则使用 GITHUB_TOKEN 或申请 OIDC 身份令牌。

| 执行与访问路径 | 通常如何认证 |
|---|---|
| GitHub 托管 Runner → GHCR | 使用 GITHUB_TOKEN，不必因此定制 OIDC |
| 自建 Runner → GHCR | 同样可使用 GITHUB_TOKEN，不因机器在外部就改用 OIDC |
| 任一种 Runner → 外部云服务 | 可采用 OIDC，由外部服务核验并授权 |

Runner 注册到 GitHub 是另一套接入机制，不是靠仓库 OIDC 设置完成。只有目标服务的信任规则限制 Runner 类型，或仓库、环境等身份条件变化时，才需要相应核对并调整信任配置。

#### 本项目当前选择与状态

- **Runners：**不添加自建 Runner，首期使用 GitHub 托管环境。
- **OIDC：**目前发布 GHCR 使用 GITHUB_TOKEN，暂不定制该栏目；将来外部云访问或某些签名方案确有需要时再评估。
- **Policies：**已在实战 7 解释用途与场景；当前不修改，也不为此升级套餐。

以上是方案与建议，不代表已经运行构建、注册机器或验证 OIDC。服务器拉取私有镜像的授权也应另外配置，不能把 CI 的短期工作证当作服务器长期凭据。

**通用理解：Runner 回答“任务在哪里执行”，OIDC 回答“怎样证明任务身份”，访问凭据与权限回答“最终允许操作哪些资源”。这三件事有关联，但不能互相替代。**

参考：[GitHub Runner 概念](https://docs.github.com/en/actions/concepts/runners)、[OpenID Connect 官方说明](https://docs.github.com/en/actions/concepts/security/openid-connect)。

### 实战 7：Policies——工作流启动前的门卫

#### 从升级提示理解它的真正作用

页面显示“尚未创建 policies”，并提示当前私有仓库的 rulesets 不会强制生效，需要迁入 GitHub Team 组织账号。这不是说免费的 Actions 没有规则，而是**这一层平台执行保护在当前仓库不生效**。

Policies 可以理解为门卫：**工作流 YAML 是进门后怎么干活的流程单；Policies 是进门前核验谁有资格启动、什么事件允许启动的规则。**目前官方说明的主要规则包括触发者（用户、角色、应用等）与事件（push、PR、手动运行等）。此功能处于公开预览，后续可能调整。

#### 场景一：允许协作者提交代码，不允许他启动自动化

假设以后请一位临时协作者帮忙开发。他需要写权限提交代码，但团队不希望他启动会消耗资源或访问敏感资源的工作流。

如果只在 YAML 中写条件，有权修改并推送该文件的人，在适用触发路径下可能连条件一起修改。管理员在工作流之外配置生效的触发者白名单，就可以另设一道门槛：

```text
协作者提交代码
→ YAML 满足触发条件
→ 平台门卫检查触发者
→ 不在允许范围内，阻止运行
```

在没有策略管理权或适用绕过权限的前提下，协作者不能仅靠修改 YAML 越过这道限制。这也可能阻止他的正常 CI，因此要按协作需求设计规则，不能只追求“越严格越好”。

#### 场景二：避免误用高风险触发事件

团队决定禁止 `pull_request_target` 触发工作流，但有人从网上复制的模板里带有这个事件。人工约定可能被忘记，生效的事件策略可以在启动前拦截它，即使 YAML 已经写进去也不运行。

该事件本身不是恶意功能；风险在于错误地结合较高权限执行未审核 PR 的代码。这个例子说明：**平台策略能约束一份错误配置的流程单，而不只是依赖每个作者自觉。**

#### 不启用，是否所有协作者都能运行任务？

不能把“贡献者”“能看到仓库的人”“有写权限的协作者”混为一谈。默认情况下，**拥有仓库写权限的协作者具备触发工作流的能力**，但还要满足具体条件：

| 方式 | 必要条件示意 |
|---|---|
| 点击 Run workflow | 有写权限，且工作流支持手动触发 |
| 推送代码触发 | 能推送到相应分支，并满足事件、分支、路径等条件 |
| 提交 PR 触发 | 配置了对应事件，且符合 Fork、审批等适用规则 |

不是每个贡献者都能任意运行所有任务，也不是只有仓库所有者才能运行。**邀请了有写权限的成员，就应按他们能触发自动化来设计安全边界。**

前面设置的只读 GITHUB_TOKEN 管“任务启动后默认能做什么”，并不禁止协作者触发任务，也不是无法在 YAML 中调整的权限上限。人的触发权限与任务的资源访问权限需要分别考虑。

#### 当前选择，以及未来何时重看

**目前不修改这个配置，也不为此升级套餐。**继续使用工作流触发条件、必要权限和人工审核；但这些不能冒充平台已经强制执行的人员限制。尤其不能把“约定只有负责人发布”写成“技术上只有负责人能发布”。

以下情况出现时，再评估付费平台执行保护：协作者增多或信任程度不同、多个仓库需要统一限制、自动化持有重要资源权限，或需要防止成员通过修改 YAML 绕过约定。

本案例未创建或启用策略；当前套餐限制依据用户提供的页面提示记录。未来采用时重新核对平台能力、套餐、规则作用范围和绕过权限。

**一句话：工作流决定怎么干，Policies 决定是否准许启动；人工约定能指导协作，但不等于门卫真的在拦截。**

参考：[GitHub Workflow execution protections](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/actions-policies/workflow-execution-protections)。

### 实战 8（收尾）：YAML、平台与 Runner 如何配合？

#### 从“流程单”串起前面所有概念

自动化规则最终写在哪里？在 GitHub Actions 中，通常是仓库 `.github/workflows/` 目录下的 YAML 文件。它描述触发条件、任务、先后依赖、运行环境、命令和权限。

但**工作流系统不等于一个 YAML 文件**：文件是定义，不会自己执行。

```text
YAML：写明什么时候做、做什么、按什么条件做
→ GitHub Actions 平台：识别事件、检查规则、调度任务
→ Runner：接收任务并执行
→ Action、脚本、编译器、Docker 等工具：完成具体操作
→ 产物、日志与状态：反馈本次执行结果
```

类比：YAML 是工序单，平台是调度室，Runner 是工位，具体工具是工位上的设备。其他平台可以使用别的配置语言或图形界面，但这些职责仍然存在。

#### Runner 不等于构建容器，一份流程也不只用一台机器

Runner 是负责执行任务的程序及其运行环境，可以依托物理机、虚拟机，也可以采用容器化方案；它不是只能打包镜像的专用容器。测试、生成报告、更新依赖等任务也能由它执行。

一份工作流可包含多个 Job，分别分配 Runner，例如测试、amd64 构建与 arm64 构建。各任务不能假定共享同一工作目录，依赖顺序和产物传递需要明确配置。

#### 仓库不是只有一份流程单

GitHub 按约定识别 `.github/workflows/` 下的 `.yml` 或 `.yaml` 文件。可以按用途拆分，文件名可自定。例如以下只是布局示例，不代表已创建：

```text
.github/workflows/
├── ci.yml                  # 检查和测试
├── publish-image.yml       # 构建与发布镜像
└── update-dependencies.yml # 定期维护依赖
```

此前页面上的“手动分支”和“多架构”就是不同文件定义的工作流。每份文件可以有自己的触发规则；同一个事件也可能触发多份工作流。

#### YAML 是入口，不一定包含全部执行细节

```text
发布工作流 YAML
├── 引用获取源码的 Action
├── 调用 scripts/test.sh 执行检查
├── 依据 Dockerfile 构建镜像
└── 调用登录、上传等工具
```

YAML 组织“先检查，再构建、发布”；脚本描述具体检查命令；Dockerfile 描述镜像制作；Action 内部也有实现代码。还可以调用可复用工作流。

因此，**YAML 不是唯一的行为来源**。理解或审核自动化时，要沿着引用查看脚本和工具，不能只看流程名称。平台权限、策略与外部服务授权，也会约束最终能做什么。

#### 自动识别不等于立即运行

文件需提交到 GitHub 的正确位置，并符合有效语法和事件要求。平台识别后，还要满足触发条件、权限与策略才能运行。

- 推送触发：检查事件、分支和路径等条件。
- 手动触发：工作流需声明对应入口，且工作流文件需要存在于默认分支。
- 定时触发：从默认分支运行。
- 被禁用或策略不允许：不能因为文件存在就照常执行。

不能理解成“任意分支放一个 YAML，就马上自动运行”。

#### 本阶段收口：配置完成不等于发布完成

用户已确认完成本阶段 Actions 栏目的配置与学习：General 按前述建议操作；Runners 不添加自建机器；OIDC 暂不定制；Policies 当前不修改、不为此升级。**这里记录用户确认，未由助手逐项读回核验网页。**

本阶段到此结束。尚未因此完成团队发布 YAML 适配、镜像构建、产物核验或生产部署；这些属于后续独立实施任务，仍遵循 7 号开发审核与生产发布 SOP（CPA 升级看 6 号），不能直接运行未经适配的官方发布流程。

**最后把整套知识连起来：流程文件决定怎么干，平台规则决定是否准许干，Runner 负责实际干，凭据限定能操作什么，日志与产物帮助验证干成了什么。**

## 一句话记住

**工作流是把一套做事方法写成可重复执行的流程；自动化平台负责在指定条件下组织机器执行。不同平台只是实现方式不同，核心都是“触发 → 输入 → 任务与规则 → 输出与反馈”。**
